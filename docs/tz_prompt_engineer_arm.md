# ТЗ: АРМ инженера препромптов (`/ai/admin/prompts/lab/`)

**Статус:** реализовано (v1, 2026-11). Документ описывает границы, данные,
сценарии и критерии приёмки; он же — основа для следующих версий.

---

## 1. Назначение

АРМ инженера препромптов — рабочее место, где разработчик препромптов
**измеряет** качество промпта режима «В чём ошибка?» на накопленной базе
ошибочных программ, сравнивает версии промпта и модели, находит слабые места
по кодам ошибок.

Это **не** «Отладка промтов» (`/ai/admin/arm/prompt-debug/`): та функция
автоматически правит промпт по провалам DL. Здесь ничего не правится
автоматически — только измеряется и показывается человеку.

### Non-goals

- автоматическое улучшение промпта (LLM-as-judge, автопатчи) — запрещено:
  оценка должна быть детерминированной;
- проверка кода запуском (компиляция C-MPA) — вне scope v1;
- замена преподавателя: АРМ измеряет промпт, а не студента;
- хранение персональных данных студентов.

## 2. Пользователи и права

| Роль | Кто | Что может |
|---|---|---|
| Инженер препромптов | разработчик промптов, преподаватель | запускать прогоны, пополнять базу, смотреть метрики |
| Контент-владелец | Самойлович / Беспалов | добавлять группы, программы, метки; не удаляет историю |
| Разработчик | staff-уровень | то же + удаление кейсов/групп |
| Суперюзер | владелец системы | всё |

Доступ — ключ `page.prompt_lab` (встроенные группы «Разработчик промптов» и
«Разработчик», миграция 0081). Тем же ключом открывается база
`FindErrorCaseGroup` / `FindErrorCase` и JSON/CSV-эндпоинты лаборатории.
Удаление кейсов/групп — только staff/superuser.

Документация — глава `find-error-prompt` (ключ `docs.prompt_developer`).
Промпты режима — обычные `Prompt(mode="find_error")`.

## 3. Данные

### 3.1 База ошибочных программ

```text
FindErrorCaseGroup   — задача/папка: условие, язык, тема, dl_node_id/course_id
  └── FindErrorCase  — программа: код, статус, source_hash, source_ref
        └── FindErrorCaseLabel — метка: код каталога + текст ошибки
```

Статусы кейса: `draft` (черновик), `ready` (готова), `verified` (проверена),
`disabled` (исключена из прогонов).

`source_ref` — уникальный стабильный ключ импорта:
`<dataset>/<группа>[/<кейс>]`. `source_hash` — sha256 кода и меток: импорт
обновляет кейс только при изменении хэша, поэтому ручные правки не затираются.

### 3.2 Каталог ошибок

`ai/services/find_error_catalog.py::ERROR_CATALOG` — коды 1–18, 20–22
(кода 19 нет). Единственный источник подписей, валидации меток и служебной
инструкции. Расширение каталога — правка таблицы, не миграция.

### 3.3 Прогоны

```text
PromptLabRun     — снимок: промпт, общий промпт, модели, кейсы, язык, суффикс
  └── PromptLabResult — пара «модель × кейс»: сообщение, ответ, коды, метрики
```

Снимки промпта и отправленного сообщения хранятся в прогоне, поэтому старый
результат можно разобрать после правки промпта. `AIRequestLog` получает по
строке на каждый вызов (`source=arm`, `mode=prompt_debug`, `batch_run_id=""`),
чтобы расход был виден в «Контроле токенов» и не смешивался с пакетными
прогонами.

## 4. Импорт и пополнение

### 4.1 Импорт из папки

```bash
python manage.py import_find_error_cases "<корень>" \
  --dataset odnomerny_massiv --language "C-MPA" --topic "Одномерный массив" \
  [--create-missing] [--fetch-statements --session-id <DLSID>] \
  [--statement-source auto|task|dl|info] [--force] [--dry-run]
```

Читает `<группа>/<кейс>/1.mpc` (UTF-8), `error_N.txt` (cp1251), `url.txt`
(`nid`/`cid`), `info.txt` (условие). Приоритет условия: локальная `Task` → DL →
`info.txt`. Без `--create-missing` отсутствующий язык/тема — ошибка со списком
доступных значений (контент-владельцы заводят их осознанно).

### 4.2 Ручное пополнение

1. Группа: название, датасет, язык, тема, `dl_node_id`/`dl_course_id`,
   условие (вручную или action «Загрузить условие из DL»).
2. Программа: группа, название, код, статус.
3. Метки: код из каталога + текст (inline).
4. Проверенная программа получает `verified`; сомнительная — `draft`.

## 5. Сценарии

1. **Бенчмарк промпта.** Выбрать промпт, 2–3 модели, 20 кейсов → сводка
   precision/recall/F1/exact и сетка по кейсам.
2. **Сравнение версий.** Тот же набор кейсов и моделей на `v1` и `v2`;
   сравнить метрики и списки пропущенных кодов.
3. **Сравнение моделей.** Один промпт и набор кейсов, разные модели:
   видно, какая модель лучше понимает каталог.
4. **Слабые коды.** По `per_code` найти коды с низким recall и открыть
   соответствующие кейсы.
5. **Регрессия.** После правки промпта повторить прогон на всём наборе
   `verified`-кейсов; падение exact rate — сигнал отката.
6. **Пополнение.** Контент-владелец добавляет новые размеченные программы;
   следующий прогон автоматически включает их (если статус не `disabled`).

## 6. Метрики

Для пары «модель × кейс»:

- `expected` — коды меток кейса;
- `parsed` — коды из последней строки `КОДЫ:` ответа;
- `matched = expected ∩ parsed`;
- `missed = expected − parsed`;
- `extra = parsed − expected`;
- `exact = (parsed == expected)`;
- `precision = |matched| / |parsed|`, `recall = |matched| / |expected|`,
  `F1 = 2PR/(P+R)`.

Пустые множества: если ожиданий и находок нет — точное совпадение и метрики
1.0; если находок нет, а ожидания есть — recall 0, precision 0 (кроме случая
«ожиданий нет»). Сводка по модели — micro-усреднение (суммируем числители и
знаменатели), exact rate — доля точных пар. `per_code` показывает по каждому
коду: сколько раз ожидался, найден, пропущен, лишний, и recall.

«Найденной» считается ошибка, код которой попал в строку `КОДЫ:`. Ошибка,
названная только прозой, не засчитывается — это цена детерминированности.

## 7. Архитектура раннера

- `start_prompt_lab_run` валидирует вход (1–5 моделей, 1–100 кейсов, промпт
  режима `find_error`), создаёт `PromptLabRun` и запускает координатор.
- Координатор запускает по потоку на модель; поток идёт по кейсам:
  `MessageComposer.compose(type=3)` → (опционально) суффикс `КОДЫ:` →
  `async_to_sync(handler)` с уникальным `client_id` → парсинг → запись
  `PromptLabResult` (в транзакции) → `AIRequestLog`.
- До 2 попыток на вызов; сбой одной пары не роняет прогон.
- `_LAB_JOBS` — live-прогресс в памяти; БД — источник правды.
- Отмена: флаг между кейсами; координатор финализирует `cancelled`.
- Orphan: если прогон `running`, живого job нет и прошло > 60 с — `failed`
  «Процесс потерян».
- По завершении всех моделей считается отчёт и сохраняется в `run.report`.

Лимиты: `PROMPT_LAB_MAX_CASES = 100`, `PROMPT_LAB_MAX_MODELS = 5`.

## 8. UI и URL-map

| URL | Назначение |
|---|---|
| `/ai/admin/prompts/lab/` | страница: форма, кейсы, процессы, результаты |
| `/ai/admin/prompts/lab/start/` | POST JSON — запуск |
| `/ai/admin/prompts/lab/status/?run_id=` | GET — снапшот для поллинга (2 с) |
| `/ai/admin/prompts/lab/cancel/` | POST JSON — прервать |
| `/ai/admin/prompts/lab/result/<id>/body/` | GET — сообщение и ответ пары |
| `/ai/admin/prompts/lab/export/?run_id=` | GET — CSV (UTF-8 BOM, `;`) |
| `/ai/admin/ai/finderrorcasegroup/` | база: группы |
| `/ai/admin/ai/finderrorcase/` | база: программы и метки |

Пустые состояния: нет кейсов/моделей — кнопка запуска недоступна и написано,
чего не хватает; нет результатов — «Пока нет завершённых пар». Ошибки
сессии/прав показываются текстом, а не падением `JSON.parse`.

## 9. Версионирование и A/B

- Версия промпта — отдельная запись `Prompt` с суффиксом `(v2)` в названии.
- Прогон хранит снимок текста и `prompt_id_snapshot`, поэтому сравнение
  остаётся корректным после правок.
- Сравнивать можно только прогоны на одинаковых наборах кейсов и моделях.
- Служебный суффикс `КОДЫ:` — часть лабораторного измерения, не production.

---

## 10. Безопасность и стоимость

- Запуск — только держатель `page.prompt_lab`; удаление — staff/superuser.
- Один прогон — до 100 кейсов × 5 моделей; UI предупреждает при > 20 кейсов.
- Каждый вызов логируется в `AIRequestLog` (токены, длительность, ошибки).
- Условие из DL тянется от имени текущего администратора (DLSID); при
  отсутствии сессии — понятная ошибка, фолбэк на `info.txt`.
- Модели/ответы — недоверенный текст: в UI экранируется перед вставкой.

## 11. Критерии приёмки v1

1. Импорт реальной папки даёт 2 группы / 76 кейсов / 120 меток; повторный
   импорт — «пропущено 76».
2. Ручная правка метки сохраняется при повторном импорте без `--force`.
3. `seed_find_error_prompt` создаёт промпт; повтор без `--force` не
   перезаписывает; `--force` обновляет.
4. На `/ai/find-error/` для C-MPA + «Одномерный массив» промпт выбран
   автоматически и уходит студенту.
5. Прогон 20 кейсов × 2 модели завершается; в БД есть `PromptLabResult` с
   `message`, `parsed_codes`, `expected_codes`; сводка и сетка корректны.
6. Прогон можно прервать; после перезагрузки страницы результат открывается;
   потерянный прогон помечается `failed`.
7. CSV скачивается и открывается в Excel без кракозябр.
8. Доступ без ключа — 403; staff/superuser — 200.
9. `python manage.py test ai --settings=DjangoTest.test_settings` — зелёный.

## 12. Открытые вопросы

- Качество меток: спорные кейсы помечать `draft`; нужна ли вторая разметка?
- Условия задач: DL может отдавать 403 студенческому DLSID — насколько
  надёжен `info.txt` как постоянный источник?
- EN/FR: промпт сидируется по-русски; нужен ли перевод каталога и суффикса?
- Слияние с «Отладкой промтов»: общий журнал/навигация возможны, но модели
  статистики держим раздельно.
- Компилятор C-MPA: проверка кода запуском дала бы более сильную метрику, но
  требует отдельного сервиса.
