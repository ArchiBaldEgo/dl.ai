## 1. StringBuilder вместо склейки строк в цикле

**Простыми словами.** Строка в Java — как записная книжка на печатных страницах:
в неё нельзя дописать строчку в середину, можно только завести НОВУЮ книжку,
переписать туда всё старое и добавить строчку. В цикле это значит: на каждом
шагу переписывается вся накопленная строка заново. Ты хотел добавить 10 строк,
а на деле переписал 1 + 2 + 3 + ... + 9 строчек — почти квадрат от количества
(данных в 10 раз больше — времени не в 10 раз, а в ~100 раз больше; такая
зависимость по науке называется «O(n²)», дальше в задачах будет ещё).

Решение называется `StringBuilder` — это как книжка-черновик с полями: можно
писать и писать, а перепечатывается всё ОДИН раз, когда ты сказал «готово».

**Есть ли это в проекте сейчас (как это выглядит «до»).**
Поиск: `+ "` — и смотреть, где поперёк цикла; ещё искать `+=` по строке.
Такой код обычно живёт там, где собирают длинный текст: отчёт, HTML-страницу,
сообщение пользователю, список «всех задач подряд». У новичка это выглядит так:

```java
String report = "";
for (Task t : tasks) {           // tasks — скажем, 500 задач
    report += t.getName() + "\n"; // каждая += переписывает ВЕСЬ отчёт заново
}
```

Если в проекте такого места нет — всё равно прочитай: склейка строк в цикле
будет на каждом проекте.

**«После» — исправленный код:**

```java
StringBuilder sb = new StringBuilder();   // черновик-книжка: один раз завёл
for (Task t : tasks) {
    sb.append(t.getName()).append('\n'); // дописываем БЕЗ переписывания
}
String report = sb.toString();            // перепечатка ровно один раз, в конце
```

**Что сделать (по шагам):**

1. Выбери ОДНО место из поиска (самое горячее — в самом глубоко вызываемом
   методе или с самой большой коллекцией).
2. Замерь до: закажи этому методу коллекцию в 10 000 элементов и оберни
   `System.nanoTime()` вокруг цикла; запиши число.
3. Замени код на `StringBuilder`.
4. Замерь ещё раз тем же способом и той же коллекцией; сравни.

**Как проверить.** Время построения строки из 10 000 элементов. Ожидание:
уменьшение примерно в десятки раз. Если почти не изменилось — либо место не
в цикле, либо коллекция всегда крошечная: тогда оптимизация не нужна, это
тоже нормальный результат («замер показал — менять не стоило»).

### У нас в проекте (DL.AI) — тот же приём
У нас Django/Python, а строки там тоже неизменяемые — принцип переносится
дословно: большие тексты (сводка пакетного прогона, запрос к модели) собираются
списком кусочков и одним `"".join(...)` в конце — питоновский `StringBuilder`.
Плюс: одна «перепечатка» вместо сотен копий. Минус: код чуть шумнее — читаются
отдельные кусочки, а не «строка растёт на ходу».

## 2. try-with-resources: файлы и потоки закрываются сами

**Простыми словами.** Открыть файл — это как сдать себе ключ от кладовки:
система выдаёт тебе доступ (`FileReader`, `InputStream` — их называют
«дескриптор»), и этих ключей в ОС есть КОНЕЧНЫЕ число. Поработал и закрыл
(`close()`) — ключ вернулся. Но если в коде случится исключение до `close()`,
метод выбрасывает его и убегает, а ключ остаётся в руке. Так кладовки
(файлы, соединения, сокеты) кончаются, и приложение падает — «too many open
files» — иногда даже ночью и на другом коде.

`try-with-resources` — это приём: ключи, выданные в скобках после `try`,
сдаюся обратно автоматически — даже при исключении. Ручной `finally { close() }`
не нужен.

**Есть ли это в проекте сейчас (как «до»).**
Поиск: `new FileReader`, `new FileInputStream`, `new BufferedReader`,
`close()` — и проверяй: кто закрывает и что будет, если посреди работы
выбросить исключение? Обычно такой код живёт: чтение/запись файлов на диске,
импорт/экспорт, логи. У новичка «до»:

```java
BufferedReader reader = new BufferedReader(new FileReader(path));
try {
    // читаем; если здесь случится IOException — reader НЕ закрылся
    return reader.readLine();
} finally {
    reader.close(); // и это уже «двойная» ручная работа, надо помнить всегда
}
```

**«После»:**

```java
try (BufferedReader reader = new BufferedReader(new FileReader(path))) {
    // скобки после try = «ключ выдан на время блока»
    return reader.readLine();      // исключение? — close() вызовется сам
} catch (IOException e) {
    // и ПОСЛЕ этого reader уже гарантированно закрыт
    return "";
}
```

**Что сделать:**

1. Поиск по всем местам, где открывается файл/поток.
2. Замер до: запускай метод много раз подряд (например, 1000 раз) и следи за
   числом открытых дескрипторов (в IDEA/Linux: `lsof -p PID | wc -l`, Windows:
   монитор ресурсов), особенно после «сломанной» версии, где бросается
   исключение. Запиши.
3. Переведи каждое место на try-with-resources.
4. Замер после: тот же цикл, тот же счётчик дескрипторов.

**Как проверить.** Один и тот же прогон 1000 раз (в том числе с исключением
в середине) должен оставить число открытых дескрипторов неизменным. «До» оно
растёт с каждым запуском, «после» — стоит на месте.

### У нас в проекте (DL.AI)
Файлы и сетевые потоки открываются только через контекст-менеджеры
(`with open(...)`) — питоновский try-with-resources: «ключ» вернётся даже при
исключении (так читается сохранённый полный лог прогона тестов под
logs/test_console/). Плюс: про дескрипторы не думаем вообще. Минус: если
внутри `with` вытащить открытый объект в наружную переменную и продолжить им
пользоваться — гарантию можно случайно обойти: работаем строго в пределах with.

## 3. Пул соединений с базой вместо нового на каждый запрос

**Простыми словами.** Соединение с базой — это не «строчка в коде», это
настоящая поездка по сети: рукопожатие, вход по логину-паролю, выделение
ресурсов. Десятки миллисекунд на каждый вызов. Если у тебя соединение
открывается на каждый запрос пользователя — это как вызвать такси, доехать
до угла, уехать и снова вызвать такси на ту же работу.

Пул соединений (`HikariCP` — самая популярная реализация; само понятие —
«пул» = «запас готовых объектов, которые берут и возвращают») — это пара
машин во дворе: нужно — сел и поехал, доехал — вернул. Один такой пул заводят
на всё приложение при старте.

**Есть ли это в проекте сейчас (как «до»).**
Поиск: `DriverManager.getConnection` — если это вызывается не один раз при
запуске, а внутри кода, который работает в ответ на запрос пользователя
(сервлет, обработчик, контроллер), — это оно:

```java
public List<Task> listTasks() {
    Connection conn = DriverManager.getConnection(url, user, password); // новое соединение — КАЖДЫЙ раз
    try { /* запросы */ } finally { conn.close(); }
}
```

**«После»:**

```java
// при старте приложения ОДИН раз (например, в главном классе):
HikariConfig cfg = new HikariConfig();
cfg.setJdbcUrl(url);        // адрес базы
cfg.setUsername(user);
cfg.setPassword(password);
cfg.setMaximumPoolSize(10); // максимум «машин во дворе»
DataSource pool = new HikariDataSource(cfg); // сам пул

// в коде запроса:
try (Connection conn = pool.getConnection()) { // берём готовое, не «вызываем такси»
    // запросы — точно те же, что раньше
} // return внутрь пула — автоматически, как и close в задаче 2
```

**Что сделать:**

1. Добавь `HikariCP` в зависимости (pom.xml / gradle).
2. Замерь до: время одного запроса-операции (список задач) с новым
   соединением — `System.nanoTime()` вокруг метода; запиши среднее из 10 прогонов.
3. Замени создание соединения на пул.
4. Замерь после: те же 10 прогонов.

**Как проверить.** Среднее время одной операции падает (обычно на
десятки миллисекунд — как ты набрал «до»). Число соединений с базой на
стороне самой базы не растёт бесконечно, а фиксируется (в базе: `SHOW
processlist` — их не больше размера пула).

### У нас в проекте (DL.AI) — буквальный пул
У нас пул не с базой, а с браузерами: Web DeepSeek (:3000) и Web Kimi (:3001) —
это пул ГОТОВЫХ Chrome-ботов, а не «запустить браузер заново на каждый вопрос».
Это ровно HikariCP: N готовых «машин во дворе» + health-check с авто-перезапуском,
если бот упал. Плюс: ответ мгновенный, ресурсы тратятся на N живых ботов, а не
на старт нового браузера в каждом запросе. Минус: пул надо обслуживать — падение
бота должно замечаться само (у нас — автопроверка), иначе пользователи упрутся
в «мёртвую машину во дворе».

## 4. PreparedStatement: параметры отдельно от SQL, а не вклеены в текст

**Простыми словами.** Запрос к базе — это письмо, которое база читает и
разбирает. Если каждый раз вклеивать в текст письма значения, получается
два беды: (1) база заново разбирает письмо, хотя меняется только значение;
(2) если значением управляет пользователь, он может вклеить в письмо СВОИЙ
текст — например, вместо id написать `1 OR 1=1` и получить вообще все строки
или даже стереть таблицу. Это называется SQL-инъекция — классическая дыра в
безопасности, и она приходит РОВНО из такого кода.

`PreparedStatement` — это бланк с полями: SQL один раз подготовлен, а
значения вкладываются в поля-вопросики. Вклеить туда произвольный текст
нельзя в принципе — там он всегда только значение.

**Есть ли это в проекте сейчас (как «до»).**
Поиск: `executeQuery` — и рядом смотреть, встречается ли SQL, собранный
склейкой. Обычно это методы «найти задачу по номеру», «найти пользователя по
логину». У новичка «до»:

```java
ResultSet rs = stmt.executeQuery(
    "SELECT * FROM task WHERE node_id = " + nodeId); // значение ВКЛЕЕНО в текст
```

**«После»:**

```java
try (PreparedStatement ps = conn.prepareStatement(
        "SELECT * FROM task WHERE node_id = ?")) {   // ? = поле для значения
    ps.setInt(1, nodeId);                            // значение — ОТДЕЛЬНО, по номеру
    try (ResultSet rs = ps.executeQuery()) {         // бланк подготовлен и посылается
        // чтение результата — без изменений
    }
}
```

**Что сделать:**

1. Пройдись по всем `executeQuery`/`executeUpdate` со склейкой и переведи на
   `?` + `setInt`/`setString`.
2. Замер до: время повторного запроса «найти задачу по id» (100 прогонов).
3. Переведи.
4. Замер после: те же прогоны, плюс тест безопасности (ниже).

**Как проверить.** Две штуки. (1) Безопасность: попробуй передать в параметр
«зловредную» строку `' OR 1=1 --` — с PreparedStatement она должна стать
значением, по которому ничего не найдено, а данными по-прежнему не залезть.
(2) Скорость: повторный запрос того же SQL быстрее — база кеширует разобранный
бланк. И то и другое записываешь в таблицу.

### У нас в проекте (DL.AI)
В Django ORM чужое значение в текст SQL вклеить негде — запросы всегда
параметризованы, класс дыры закрыт «по построению». А правило «в текст ничего
чужого не вклеивать» работает у нас и вне SQL: имя файла лога тестов проходит
через регулярку-барьер (`_LOG_FILENAME_RE`) — ровно против «вклейки» `../` в
путь. Плюс: не надо напоминать каждому разработчику про инъекции — способ
запроса сам не позволяет. Минус: ORM скрывает SQL, и медленный запрос легко
не заметить — надо уметь смотреть, какой SQL родился (лог базы/EXPLAIN).

## 5. N+1 запросов: все связанные данные — одним JOIN, а не по одному

**Простыми словами.** Веб-страница показывает список задач. В коде это
выглядит честно и безобидно: «возьми все задачи, потом для каждой возьми
её язык и тему». Но посчитай: 1 запрос на список + по одному запросу на
каждую задачу для языка + по одному на тему = для 100 задач — 201 запрос.
Каждый запрос — это поездка в базу и обратно (см. задачу 3). Похоже, как
если бы из склада для сборки одного стула ты ездил по ОДНОЙ детали за раз.
Такое поведение называется N+1 запросов (1 «мама»-запрос + N «детских»).

Решение — `JOIN`: один запрос, который сразу прицепляет связанные строки
(«дай все задачи и рядом их языки»).

**Есть ли это в проекте сейчас (как «до»).**
Поиск: `for` — и внутри цикла смотреть `executeQuery` / метод, который лезет
в базу. Типичное место — метод, готовящий список для таблицы/отчёта:

```java
List<Task> tasks = taskDao.findAll();      // запрос 1
List<TaskView> rows = new ArrayList<>();
for (Task t : tasks) {                     // цикл по N задач
    String lang = langDao.findById(t.getLanguageId()); // запросы 2..N+1
    rows.add(new TaskView(t.getName(), lang));
}
```

Как СЕБЯ поймать: включи лог SQL (у пула HikariCP — счётчик, или `lsof`/лог
базы) и посчитай запросы на одну загрузку страницы со списком: если сотни —
это оно.

**«После»:**

```java
PreparedStatement ps = conn.prepareStatement(
    "SELECT t.id, t.name, l.name AS lang_name "
  + "FROM task t JOIN language l ON l.id = t.language_id");
try (ResultSet rs = ps.executeQuery()) {   // ОДИН запрос «мама + дети сразу»
    while (rs.next()) {
        rows.add(new TaskView(rs.getString("t.name"), rs.getString("lang_name")));
    }
}
```

**Что сделать:**

1. Замер до: посчитай SQL-запросов на страницу (лог) и время построения
   списка; запиши.
2. Найди цикл «по списку — запрос в базу». Перепиши на JOIN из одной выборки.
3. Замер после: тот же счётчик запросов (должен стать 1–2) и то же время.

**Как проверить.** «SQL-запросов на страницу: было сотни — стало 1»; время
загрузки списка падает в разы.

### У нас в проекте (DL.AI)
Дневной отчёт делает ровно это: школа/группа студентов подтягивается ОДНИМ
запросом по списку внешних id (`filter(external_user_id__in=...)`), а не
запросом на каждую строку; справочник заведений — вообще один запрос на всю
страницу. Плюс: сотни строк — это 2–3 запроса, а не сотни. Минус: список id
надо собрать заранее — код чуть длиннее «наивного» цикла, и его легко
откатить к наивному при правках, если не помнить, зачем так.

## 6. Пагинация: не тянуть ВСЕ строки, когда показывают первые 50

**Простыми словами.** Пока таблица маленькая, «спроси всё и покажи» —
нормально. А когда её стало 10 000 строк — это как библиотека, которая на
«можно первые 2 книги?» выносит тебе ВЕСЬ стеллаж: время на тележку, память
на складе рядом с тобой, а читаешь всё равно первые страницы. Пагинация —
это «отдай первые 50» (`LIMIT 50`) и «отдай следующие 50» (`OFFSET 50`)
или, на очень большом объёме, «отдай 50 строк после id X» (это называется
«keyset-пагинация», OFFSET на больших номерах тормозит сам).

**Есть ли это в проекте сейчас (как «до»).**
Поиск: `SELECT *` (и findAll в DAO) — и проверяй: есть ли LIMIT?
Обычно страдают страницы-списки/журналы, которые росли сами собой:

```java
public List<Task> listForPage(int page) {
    return query("SELECT * FROM task"); // 10 000 строк? — все 10 000 уйдут в память и в HTML
}
```

**«После»:**

```java
public List<Task> listForPage(int page, int size) {
    PreparedStatement ps = conn.prepareStatement(
        "SELECT * FROM task ORDER BY id LIMIT ? OFFSET ?"); // только кусок
    ps.setInt(1, size);          // сколько строк — 50
    ps.setInt(2, (page - 1) * size); // со скольки начинается эта страница
    // … чтение — как раньше; остальные 9 950 строк НЕ трогались
    return rows;
}
```

**Что сделать:**

1. Замер до: время ответа страницы-списка на 10 000 строк и память под
   список (`Runtime.totalMemory() - freeMemory()` вокруг метода).
2. Вариант с LIMIT/OFFSET (выше), «следующая страница» = больше OFFSET.
3. Замер после: тот же замер.

**Как проверить.** Время ответа и память падают примерно в «размер таблицы /
размер страницы» раз; кнопка «следующая страница» работает; последняя
страница (OFFSET за концом) просто возвращает пустое — это норм.

### У нас в проекте (DL.AI)
У админки Django чанглисты пагинированы сами. А ещё у нас — измеренное
правило: «Show counts» выключено (`show_facets = NEVER`) во всех списках с
фильтрами: Django считал COUNT(*) на каждый вариант фильтра, и это реально
тормозило загрузку больших журналов. Плюс: страницы открываются быстро.
Минус: счётчиков по вариантам фильтра не видно — сознательная сделка
«наглядность → скорость».

## 7. Кеш справочников: словари, которые не меняются, читаем один раз

**Простыми словами.** В каждом проекте есть справочники: список языков,
тем, групп. Они меняются раз в месяц (кто-то дописал новую тему), но читают
их из базы на каждом запросе каждой страницы. Это как за солью для каждого
супа ходить в отдельный магазин на другом конце города: соль же уже дома.

Кеш в памяти — это «солонка на столе»: прочитали справочник из базы один раз,
дальше — из памяти (структура `ConcurrentHashMap` — это словарь, у которого
одновременно могут читать много потоков без взаимных поломок; для обновления
обертывают в `AtomicReference`). Один раз в час (или по кнопке «обновить
справочник») ходим в кладовку — и всё.

**Есть ли это в проекте сейчас (как «до»).**
Поиск: имя таблицы справочника (`FROM language`, `FROM topic`, `FROM group`)
— если оно встречается в коде, который вызывается на каждый запрос, — это оно:

```java
public String langName(int id) {
    return jdbcTemplate.query(          // запрос в БД — на КАЖДЫЙ вызов
        "SELECT name FROM language WHERE id = ?", id);
}
// а вызывается langName в цикле по всем задачам → N+1 СВЕРХУ
```

**«После»:**

```java
private static final AtomicReference<Map<Integer, String>> LANGS =
    new AtomicReference<>(Map.of());    // «солонка»: словарь целиком, в памяти

static { LANGS.set(loadLangs()); }      // при старте прочитали из базы

private static Map<Integer, String> loadLangs() { /* SELECT id, name FROM language */ }

public String langName(int id) {        // БД НЕ вызывается — берём из памяти
    String name = LANGS.get().get(id);
    return name == null ? "?" : name;
}

// обновление раз в час (таймер) или по кнопке админа:
// LANGS.set(loadLangs()) — новый словарь, старый уходит сам (чтение не ломается)
```

**Что сделать:**

1. Замер до: счётчик запросов к таблице справочника за минуту под нагрузкой
   (лог SQL) + время ответа страницы, где справочник читается.
2. Заведи кеш, обновление по таймеру.
3. Замер после: тот же счётчик.

**Как проверить.** Счётчик запросов к справочнику падает с «тысяч в минуту»
до единиц (только обновления); время ответа списка падает — особенно если
у тебя совпали задачи 5 и 7 (справочник читался в цикле).

### У нас в проекте (DL.AI)
Кешируем «кто вошёл»: user_info от dl.gsu.by лежит в сессии на
AI_AUTH_CACHE_TTL секунд, а если dl.gsu.by совсем упал — отдаём последний
кешированный ответ вместо 503. История переписки живёт в Redis/кеше, общей
для всех процессов. Плюс: сервис переживает отказ источника и не дёргает его
на каждый запрос. Минус: данные могут устареть ровно на TTL (новое имя
пользователя появится после кеша), а обновлённый справочник моделей требует
принудительного «свипа» — у нас для этого отдельная команда с флагом --force.

## 8. Спискам — лёгкие колонки: тяжёлое тело грузим отдельно

**Простыми словами.** Иногда у таблицы есть колонка с очень длинным текстом:
текст задачи, код решения, XML-отчёт. Если список берёт `SELECT *`, он
тянет эти килобайты для КАЖДОЙ строки × на все строки — хотя пользователь
видит только имена и даты, а развёртка «показать код» открывает ОДНУ строку.
Это как тащить весь чемодан, чтобы посмотреть, какая рубашка внутри.

Решение: список выбирает только лёгкие колонки (`SELECT id, name, sent_at`),
тяжёлое тело — отдельный запрос при клике («покажи решение этой задачи»).

**Есть ли это в проекте сейчас (как «до»).**
Поиск: `SELECT *` в методах списка/журнала; особенно там, где рядом есть
колонки вида `code`, `text`, `response`, `body`. У новичка это редко выглядит
«плохим кодом» — выглядит просто как «обычный запрос» — и этим опасно:

```java
List<SolutionRow> rows = query(
    "SELECT * FROM solution");   // решение — 5 КБ текста; строк 5 000 → ~25 МБ на списке
```

**«После»:**

```java
// Список:
List<SolutionRow> rows = query(
    "SELECT id, student_name, sent_at FROM solution"); // только то, что видно в таблице

// «Показать код» — отдельный запрос ровно по одной строке
Solution full = dao.findWithBody(id); // SELECT … , code FROM solution WHERE id = ?
```

**Что сделать:**

1. Замер до: память под построение списка (`Runtime.totalMemory()` минус
   `freeMemory()` до/после метода) и время ответа.
2. Перепиши SELECT списков на перечисление лёгких колонок; тело — отдельный
   запрос по id при открытии.
3. Замер после: те же метрики.

**Как проверить.** Память под список падает примерно во столько раз, сколько
«весит» тяжелая колонка; раскрывается и «до», и «после» один и тот же объём
текста в развёртке — только теперь он грузится по требованию.

### У нас в проекте (DL.AI) — почти дословно
Дневной отчёт читает записи через `.only(...)` — без message/response_text:
тексты тяжёлые, отчёту не нужны. Пакетные прогоны хранятся «лёгкими»
(light_results): таблица показывает строку без тела, а полный код/ответ модели
подтягивается отдельным запросом при раскрытии строки — тело по требованию,
как в этой задаче. Плюс: страница не таскает десятки мегабайт текста, которые
никто не открывал. Минус: раскрытие строки ходит в сеть второй раз — если
сетка лагает, «подробнее» открывается с паузой (у нас на этот случай крутится
индикатор загрузки).

## 9. Большие файлы: передать кусочками, не глотая целиком

**Простыми словами.** Если приложение отдаёт клиенту большой файл, наивный
код сначала читает его ВЕСЬ в память (`readAllBytes` — «глотнуть арбуз
целиком»), и только потом начинает передавать. Файл в 200 МБ — значит, в
машине на время передачи минимум 400 МБ (оригинал + копия в буферах) и
память JVM раздувается и мусорится.

Решение — построчная/блочная передача («арбуз кусочками»): читать буфер
8 КБ, писать его в поток ответа, снова читать… Память приложения не зависит
от размера файла — 8 КБ всегда.

Если ты сейчас в проекте вообще не отдаёшь файлы — задача читается как
учебная: описание нужно, когда такое место появится. (Замер для отчёта в
этом случае — не требуется, напиши «в проекте не встречается».)

**Есть ли это в проекте сейчас (как «до»).**
Поиск: `readAllBytes`, `readAllLines`, `Files.readString` — особенно там,
где результат отдаётся в `response`:

```java
byte[] file = Files.readAllBytes(Path.of(path)); // файл ВЕСЬ в памяти
response.setContentType("application/octet-stream");
response.getOutputStream().write(file);            // и отдаём всю копию
```

**«После»:**

```java
try (InputStream in = new FileInputStream(file);
     OutputStream out = response.getOutputStream()) { // ключи закроются сами (задача 2)
    byte[] buffer = new byte[8192]; // ковш: 8 КБ, всегда один и тот же
    int n;
    while ((n = in.read(buffer)) != -1) { // наливаешь ковш из файла
        out.write(buffer, 0, n);          // и сразу выливаешь в ответ; и так до конца
    }
}
```

**Что сделать:**

1. Замер до: отдай файл 100–200 МБ, замерь пик памяти JVM (визуальный
   профилировщик; грубый вариант — `Runtime.totalMemory()-freeMemory()`
   вокруг метода).
2. Перепиши на цикл с буфером.
3. Замер после: тот же пик памяти; скорость отдачи НЕ должна упасть заметно.

**Как проверить.** Пик памяти при отдаче файла больше не привязан к размеру
файла (200 МБ файл ≈ те же килобайты буфера, что и 10 МБ); скорость —
примерно той же.

### У нас в проекте (DL.AI)
Больших файлов мы не отдаём — здесь, как и в задаче 9, учебная часть. Но
рефлекс «не глотать целиком» у нас есть в другом месте: тело огромного ответа
модели в журнале отдаётся окнами (`?offset&length` с потолком на размер куска)
и кнопкой «Показать ещё», а не одним куском. Плюс: даже ответ в мегабайты не
замораживает страницу. Минус: для «скачать всё целиком» нужен отдельный
эндпоинт (у нас он есть — отдельно по каждой записи).

## 10. Форматтеры дат: не покупать новый будильник на каждое утро

**Простыми словами.** `DateTimeFormatter.ofPattern(...)` и, в старом API,
`new SimpleDateFormat(...)` — это не «конверт», а целенький прибор, который
строится (разбор шаблона, служебные объекты). Внутри цикла «новый форматтер
на каждую строку» — как купить новый будильник на каждое утро.
Важно и для порядка потоков: `SimpleDateFormat` НЕ безопасен (потоконебезопасен)
— если его держать общим, два потока могут испортить друг другу результат;
`DateTimeFormatter` — безопасен, его можно смело делать константой.

**Есть ли это в проекте сейчас (как «до»).**
Поиск: `new SimpleDateFormat(`, `DateTimeFormatter.ofPattern(` — и смотри,
не стоит ли это ВНУТРИ цикла или вызывается изнутри цикла (метод-форматер
дата-время из строки таблицы). Место обычно то же, что и в задаче 1 — код
собирает отчёт/таблицу:

```java
for (Row r : rows) {
    String when = new SimpleDateFormat("dd.MM.yyyy").format(r.getDate()); // новый будильник КАЖДЫЙ раз
    out.println(when + " " + r.getName());
}
```

**«После»:**

```java
private static final DateTimeFormatter RU_DATE =     // один будильник на всё приложение
    DateTimeFormatter.ofPattern("dd.MM.yyyy");       // стат. константа: проблем с потоками не будет

for (Row r : rows) {
    out.println(RU_DATE.format(r.getDateAsLocalDateTime()) + " " + r.getName());
}
// А если дата у ВСЕХ строк одна (отчёт за день) — строку даты строим ОДИН раз ДО цикла:
String day = RU_DATE.format(dayStart);
for (Row r : rows) { out.println(day + " " + r.getName()); }
```

**Что сделать:**

1. Замер до: обернуть цикл в `System.nanoTime()`, миллион итераций (или
   профилировщик — сколько времени съел `DateTimeFormatter`).
2. Вынести форматтер в `static final`.
3. Если дата сквозная — вычислять строку один раз до цикла.
4. Замер после.

**Как проверить.** Время цикла падает (миллион дат «до» — сотни
миллисекунд, «после» — единицы); профилировщик перестаёт показывать
`DateTimeFormatter` в горячих методах.

### У нас в проекте (DL.AI)
Даты форматируются из одного места: часовой пояс берётся константой MOSCOW_TZ
и единственным помощником `timezone.localtime()`; никогда не собирать
«+3 часа» вручную и не городить свой формат на месте — дата выводится при
рендере один раз (методы-дисплеи `sent_at_display` в списке журнала). Плюс:
везде одинаковый стиль и нет рассинхрона часовых поясов. Минус: правило
держится на дисциплине — один «умелец» с самодельным смещением, и в таблицах
появляется второй стиль дат. Был и реальный случай легаси: колонка базы
называется recieved_at вместо received_at (опечатка в чужом коде), и имя в
шаблонах живёт с этой опечаткой — переименование сломало бы совместимость.

## 11. (бонус) Тяжёлая работа — не в момент ответа: фон + проверка статуса

**Простыми словами.** Пользователь нажал кнопку «сделать отчёт», а работа
занимает час. Делать её, пока посетитель стоит у кассы, нельзя: браузер
крутит колесо, на 60-й секунде сервер обрывает соединение — потеряны и работа,
и посетитель. Правильно — как в ресторане: «заказ принят» мгновенно, готовность
посетитель спрашивает потом. По-научному: фоновая задача (в Java —
`ExecutorService` или очередь) + поллинг статуса («периодически спрашивать»).

**Есть ли это в проекте сейчас (как «до»).**
Поиск: длинные циклы/запросы внутри обработчика, который вызвала кнопка.
Типичное место — «сделать отчёт», «отправить письма всем», «импорт». «До»:

```java
protected void doPost(HttpServletRequest req, HttpServletResponse resp) {
    buildHugeReportAndSendEmail();   // час работы — браузер ждёт и отвалится
}
```

**«После»:**

```java
protected void doPost(...) {
    executor.submit(() -> {          // «заказ принят»: работа уходит на кухню
        buildHugeReportAndSendEmail();
        return true;
    });
    writeJson(resp, {"status": "started", "jobId": assignJobId()});
}

protected void doGetStatus(...) {    // «проверить состояние» — лёгкий опрос
    JobState st = jobs.get(jobId);
    writeJson(resp, {"status": st.status, "percent": st.percent});
}
```

### У нас в проекте (DL.AI) — так работает всё «длинное»
Пакетные прогоны ARM идут фоновым воркером: страница не замирает, а журнал и
«Мои процессы» поллингом спрашивают состояние. Обновление здоровья моделей
тоже стартует не-блокирующим вызовом. Плюс: кнопка отвечает мгновенно даже на
часовой работе, несколько прогонов видно одновременно. Минус: живую job может
съесть перезапуск процесса — у нас поэтому источник истины — БД (строки
прогона), а «живой job» — только экран, который при потере дорисовывается из
БД. И ещё: фоновое состояние надо ВИДИМО показывать человеку (у нас — меню
«Процессы»), иначе «фон» превращается в «чёрный ящик».
