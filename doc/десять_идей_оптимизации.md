# 10 задач для студента 1 курса: оптимизация Java-проекта (скорость + память)

Все задачи — для проекта на Java (веб-приложение с базой и списками/отчётами).
Каждая задача — самостоятельная работа «для полного новичка»: сначала понять,
что происходит, потом заменить код, потом доказать замером, что стало лучше.

Главное правило: **сначала измерить, потом менять, потом измерить ещё раз.**
Оптимизация «на глазок» не считается выполненной — к каждой задаче нужно
приложить таблицу «до/после» (время и/или память, см. шаблон в конце).

---

## 1. StringBuilder вместо конкатенации в цикле

**Что это:** строки в Java неизменяемые. `result = result + s;` в цикле создаёт
новую строку на каждой итерации: 1000 строк = 1000 копий всё большего размера
(примерно O(n²) времени и мусора).

**Что сделать:** найти в проекте конкатенацию в цикле и переписать через
`StringBuilder`:

```java
StringBuilder sb = new StringBuilder();
for (String s : parts) {
    sb.append(s).append('\n');
}
String result = sb.toString();
```

**Как проверить:** собрать строку из 10 000 элементов оба способа, замерить
время (`System.nanoTime()`); таблица «до/после».

## 2. try-with-resources — закрытие файлов и потоков

**Что это:** `FileReader`/`InputStream` держат файл и память ОС, пока не
вызван `close()`. При исключении обычный код «забывает» закрыть — утечка
дескрипторов.

**Что сделать:** любой код вида `close()` в `finally` или без закрытия
переписать:

```java
try (BufferedReader reader = new BufferedReader(new FileReader(path))) {
    // работа с файлом: reader закроется сам даже при исключении
} catch (IOException e) {
    // обработка
}
```

**Как проверить:** метод, который читает файл и бросает исключение на
середине; убедиться (по логам/отладчику), что поток закрыт; замерить число
открытых дескрипторов до/после в цикле запусков.

## 3. Переиспользование соединений (пул), а не новое на каждый запрос

**Что это:** открытие нового JDBC-соединения — «рукопожатие» с БД по сети,
миллисекунды и ресурсы, на каждый запрос. Под нагрузкой всё виснет.

**Что сделать:** подключить пул соединений (`HikariCP`) — один объект на всё
приложение; соединение берём из пула и отдаём обратно (`try`-блок из задачи 2).

**Как проверить:** замер среднего времени одной запрос-операции до (новое
соединение всегда) и после (пул); таблица «до/после».

## 4. PreparedStatement вместо склеенного SQL

**Что это:** SQL, собранный конкатенацией (`"... WHERE id = " + id`), каждый
раз заново разбирается базой, а значение от этого пользователя попало прямо
в текст запроса (SQL-инъекция!).

**Что сделать:** все запросы с параметрами перевести на параметры:

```java
try (PreparedStatement ps = conn.prepareStatement(
        "SELECT name FROM task WHERE node_id = ?")) {
    ps.setInt(1, nodeId);
    try (ResultSet rs = ps.executeQuery()) { /* ... */ }
}
```

**Как проверить:** попытаться передать в параметр «зловредную» строку
(`' OR 1=1 --`) — данные должны остаться целыми; время повторного запроса
(план кешируется БД) до/после.

## 5. N+1 запросов → один JOIN

**Что это:** в цикле по списку задач для каждой задачи отдельный запрос за её
языком/темой: 100 строк = 101 запрос.

**Что сделать:** получить всё одним запросом с `JOIN` и прочитать связанные
значения из той же выборки (`SELECT task.*, lang.name FROM task JOIN language
lang ON lang.id = task.language_id`); в JPA — `JOIN FETCH`.

**Как проверить:** включить лог SQL (у пула — счётчик запросов), посчитать
запросы на страницу со 100+ строками: до — сотни, после — 1–2; время загрузки
«до/после».

## 6. Пагинация вместо «SELECT * — всё на страницу»

**Что это:** таблицы отдают ВСЕ строки, даже если пользователь смотрит
первые 50. У тысяч строк растёт и память (все объекты в RAM), и время отдачи
(гигантский HTML).

**Что сделать:** SQL с ограничением и смещением:
`SELECT ... LIMIT 50 OFFSET 0` (следующая страница — `OFFSET 50`); вместо
`OFFSET` на больших объёмах — « WHERE id > ? ORDER BY id LIMIT 50».

**Как проверить:** страница со списком на 10 000 записей: время ответа и
используемая память до (все строки) и после (50 строк); кнопка «следующая
страница» работает.

## 7. Кеш справочников (языки, темы, группы) в памяти

**Что это:** справочники, которые меняются раз в месяц, читаются из БД на
каждый запрос каждой страницы — лишние запросы и время.

**Что сделать:** прочитать справочник один раз в `ConcurrentHashMap` и
обновлять по таймеру (или по явному сигналу «справочник изменился»):

```java
private static final AtomicReference<Map<Integer, String>> CACHE = new AtomicReference<>(Map.of());
// периодический рестарт: CACHE.set(loadFromDb());
```

**Как проверить:** счётчик запросов к таблице справочника до/после за минуту
под нагрузкой; время ответа страницы.

## 8. Списки без тяжёлых текстов

**Что это:** в список-таблицу тянется `SELECT *` вместе с колонками по
несколько килобайт (текст задачи, код решения). Память под список ×100
строк огромна, хотя показываем только имя.

**Что сделать:** для списков выбирать только нужные колонки
(`SELECT id, name FROM ...`), тяжёлое тело грузить отдельно по клику
(«подробнее»).

**Как проверить:** снять используемую память страницы-списка до/после
(например, `Runtime.totalMemory()-freeMemory()` до и после построения списка)
и время ответа.

## 9. Потоковая обработка больших файлов

**Что это:** файл читается целиком в память (`Files.readAllBytes`), потом
отдаётся клиенту: файл в 200 МБ = минимум 400 МБ пиковая память.

**Что сделать:** читать и отдавать кусочками (`BufferedReader` построчно /
`buffer = new byte[8192]` в цикле), сразу писать в выходной поток ответа:

```java
try (InputStream in = new FileInputStream(file);
     OutputStream out = response.getOutputStream()) {
    byte[] buffer = new byte[8192];
    int n;
    while ((n = in.read(buffer)) != -1) { out.write(buffer, 0, n); }
}
```

**Как проверить:** отдать файл 100+ МБ, замерить пик памяти JVM до/после
(визуальный профилировщик или `Runtime`); скорость отдачи не должна упасть.

## 10. Даты: раз вне цикла — одна, а не новая на каждой итерации

**Что это:** `new SimpleDateFormat()` / `LocalDateTime.now()` /
`DateTimeFormatter.ofPattern(...)` внутри цикла — на каждой итерации строится
новый форматтер (а `SimpleDateFormat` ещё и потоконебезопасен).

**Что сделать:** форматтер (`DateTimeFormatter`) — `static final` константа;
если в цикле печатается много строк с одной датой, вычислить строку даты один
раз до цикла.

```java
private static final DateTimeFormatter RU_DATE = DateTimeFormatter.ofPattern("dd.MM.yyyy");
// в цикле: только RU_DATE.format(precomputedDateTime);
```

**Как проверить:** отформатировать 1 000 000 дат до/после — время;
профилировщик должен перестать показывать `DateTimeFormatter` в горячих
методах.

## Шаблон отчёта «до/после» (прикладывается к каждой задаче)

| Параметр | До | После | Чем мерил |
|---|---|---|---|
| Время операции | 1200 мс | 40 мс | `System.nanoTime()`, 10 прогонов |
| Память (пик) | 420 МБ | 60 МБ | профилировщик / `Runtime` |
| SQL-запросов на страницу | 101 | 1 | лог пула |

+ короткое описание: что именно изменилось в коде (ссылки на строки/файлы).
