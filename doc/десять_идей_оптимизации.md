# 10 идей для студенческих задач по оптимизации (скорость + память)

Идеи универсальные: подходят и Java-проекту, и любому другому. Каждая задача —
самостоятельная работа «для полного новичка»: что делать, зачем, как убедиться,
что стало лучше. Главное правило любой задачи: **сначала измерить, потом менять,
потом измерить ещё раз**. Оптимизация «на глазок» без замера не считается
выполненной — нужно показать таблицу «до/после» (время и/или память).

---

## 1. Устранить N+1 запрос к базе

**Что это:** в цикле по списку объектов для каждого объекта выполняется
отдельный SQL-запрос (имя автора задачи, язык, тема). 100 строк = 101 запрос.

**Что сделать:** найти такой цикл (в админских списках, отчётах, журналах) и
заменить на выборку со связями за один запрос (`JOIN` / `JOIN FETCH` в Java JPA,
`select_related`/`prefetch_related` в Django ORM).

**Как проверить:** лог SQL-запросов до (N+1 штук) и после (1–2 запроса); время
загрузки страницы со 100+ строками.

## 2. Индексы под реальные фильтры

**Что это:** список фильтруется по полям, по которым нет индексов — база
сканирует всю таблицу (Full Table Scan / Seq Scan).

**Что сделать:** снять 3 самых частых фильтра из UI (пользователь, статус,
дата), включить лог медленных запросов, добавить индекс `(поле_фильтра)` или
составной `(поле1, поле2)`, сравнить `EXPLAIN (ANALYZE)`/план выполнения до
и после.

**Как проверить:** план запроса меняется с Seq Scan на Index Scan; время выборки
на таблице в 100 тыс. строк падает в разы.

## 3. Пагинация вместо «выгрузить всё»

**Что это:** страница тянет из базы ВСЕ записи (можно сотни тысяч) и рендерит
их все сразу — тратится и время, и память (HTML в браузере растёт на десятки МБ).

**Что сделать:** разбить вывод на страницы по 25–50 записей (ссылки «назад/далее»)
или на «бесконечную» подгрузку. Уже рендерится всё? Заменить на серверную
пагинацию с номером страницы в URL.

**Как проверить:** время генерации страницы и размер HTML до/после на большой
таблице; память JVM/процесса при заходе на первую страницу.

## 4. Кэш тяжёлых вычислений

**Что это:** одно и то же значение пересчитывается при каждом запросе
(итоги за день, агрегаты, ответы внешнего API).

**Что сделать:** закешировать результат на N минут (Redis / In-Memory cache /
`@Cacheable`). Отдельно решить вопрос инвалидации: сбрасывать кэш при записи
данных.

**Как проверить:** первый запрос — долго, повторные — мгновенно; после записи
новых данных кэш отдаёт свежее значение.

## 5. Потоковая (чанковая) обработка больших данных

**Что это:** весь файл/ответ целиком читается в память (`String content =
Files.readString(...)`), потом обрабатывается. Большой файл = всплеск памяти
и риск OOM.

**Что сделать:** читать/обрабывать/писать построчно или блоками (stream,
`BufferedReader`, генераторы), отдавать клиенту «лениво» (chunked response),
не склеивая всю строку в памяти.

**Как проверить:** максимальная память процесса при обработке файла 100 МБ
до/после (например, через `-Xmx64m` — старый код должен упасть или заметно
просесть, новый — работать).

## 6. Генераторы/итераторы вместо промежуточных списков

**Что это:** цепочка обработок создаёт полный промежуточный список на каждом
шаге: `list(map(...))`, `stream().collect()` несколько раз на 1 млн элементов.

**Что сделать:** заменить на однократный проход (генератор, `Stream` без
промежуточных `collect`, «ленивую» последовательность). Особенно заметно на
экспортах/импортах.

**Как проверить:** peak-memory до/после (профилировщик или замер
`Runtime.totalMemory()`); время на 1 млн элементов.

## 7. Ленивая загрузка тяжёлых полей

**Что это:** список показывает 20 колонок, из них одна — текст на 50 КБ
(ответ модели, код). Он грузится и передаётся всегда, даже когда не раскрыт.

**Что сделать:** в списке отдавать только метаданные; текст «лениво» — отдельным
запросом по клику (AJAX / lazy field / `@JsonIgnore` + отдельный endpoint).

**Как проверить:** размер ответа со списком (КБ → единицы КБ на строку),
время загрузки списка из 100 записей.

## 8. «Экономные» структуры данных

**Что это:** для пары полей создаётся тяжёлый объект (`HashMap<String,String>`
на 2 записи), строки сравниваются через `new String(...)`, числа — в
`String` и обратно.

**Что сделать:** заменить на лёгкие структуры (в Java — record вместо класса,
`EnumMap` вместо `HashMap` для ключей-энумов; в Python — `__slots__`, кортежи
вместо словарей). Избавиться от лишних конверсий типов.

**Как проверить:** peak-memory при обработке 1 млн записей до/после;
профилировщик памяти (VisualVM / Heap dump / tracemalloc).

## 9. Троттлинг и дебаунс на фронте

**Что это:** на каждое нажатие клавиши в поле поиска уходит AJAX-запрос —
сервер получает в 10–50 раз больше запросов, чем нужно.

**Что сделать:** «дебаунс» — слать запрос через 300 мс после остановки набора;
«троттлинг» — опрос статуса не чаще раза в N секунд. Добавить отмену предыдущего
незавершённого запроса (AbortController / axios cancel token).

**Как проверить:** счётчик запросов в Network-вкладке: при наборе слова из
10 букв — не больше 1–2 запросов вместо 10.

## 10. Сжатие и кеширование статики на раздаче

**Что это:** каждый заход заново скачивает одинаковые JS/CSS (сотни КБ), без
сжатия — по сети гоняется несжатый текст.

**Что сделать:** включить gzip/brotli и заголовки кеширования для статики
(`Cache-Control: public, max-age=…`) на реверс-прокси/раздаче статики;
при изменении имени файла — версионирование (`app.js?v=<hash>`), чтобы кеш
обновлялся reliably.

**Как проверить:** размер ответа на CSS до/после (в DevTools должно быть
в ~3–5 раз меньше при gzip), повторный заход — 304 или «from cache».

## Общий шаблон отчёта по любой задаче

1. Замер «до» (время и/или память) на конкретном объёме данных — цифра.
2. Ссылка на место в коде, которое менялось.
3. Замер «after» на тех же данных — цифра.
4. Вывод в одну строку: «что стало быстрее / меньше и почему».
5. Проверка, что функционально ничего не сломалось (ручной сценарий или тест).
