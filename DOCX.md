## Инструкция для пользователя

1. Назначение инструкции
Инструкция предназначена для обычного пользователя AI-интерфейса (студента, преподавателя, любого авторизованного посетителя основного сайта). Она объясняет, как войти в раздел `/ai/`, выбрать режим работы и модель, отправить сообщение, работать с задачами по программированию, искать ошибки в коде и пользоваться голосовым режимом.
Важно. Обычный пользователь не управляет моделями, справочниками и настройками AI — он работает только с теми функциями интерфейса, которые доступны на текущую дату.

2. Доступ и вход
Отдельной регистрации в AI-интерфейсе нет. Авторизация передаётся из основной сессии сайта `dl.gsu.by` через cookie `DLSID`; при первом входе учётная запись создаётся в приложении автоматически (см. `ai/middleware.py`, `ai/external_account.py`).
    1. Войти на основном сайте `dl.gsu.by`.
    2. Перейти в раздел `/ai/`.
    3. Раздел откроется сразу; отдельный логин не требуется.
    4. Если доступ не открывается — заново войти на основном сайте и обновить страницу.
Адрес `/ai/` открывает последнюю активную вкладку (Чат, Реши задачу или В чём ошибка — выбор запоминается в браузере). Конкретный режим всегда можно открыть по прямым адресам:
Страница	Адрес	Назначение
Чат с DLAI	`/ai/chat/`	Свободный диалог с моделью.
Реши задачу	`/ai/solve-problem/`	Решение задачи по программированию.
В чём ошибка?	`/ai/find-error/`	Поиск ошибки в коде.

3. Как попасть в режим «Реши задачу» со страницы задачи
Режим «Реши задачу» обычно открывают не вручную, а ссылкой со страницы задачи на основном сайте: у задачи есть кнопка перехода в AI, которая ведёт на `/ai/solve-problem/?nid=<идентификатор задачи>`.
    1. Открыть задачу на основном сайте.
    2. Нажать ссылку/кнопку перехода в AI-раздел.
    3. Условие задачи автоматически подгрузится в поле ввода (приложение получает его через `/ai/api/task-info/`).
    4. Если текст задачи не подгрузился — вставить условие в поле ввода вручную и выбрать язык программирования.
Без параметра `?nid=` страница работает как обычный «решатель»: скопируйте условие задачи в поле ввода самостоятельно.

4. Общая структура интерфейса
Интерфейс состоит из верхней панели, центральной области сообщений и правой боковой панели.
Зона интерфейса	Элементы	Назначение
Верхняя панель	Переключатель страниц (Чат с DLAI / Реши задачу / В чём ошибка?), модель, сортировка моделей, язык интерфейса, тема оформления.	Определяет режим, модель и язык ответа.
Центр	Лента сообщений, поле ввода, кнопки Send и Clear Context.	Основная рабочая область диалога.
Правая панель	Ссылка «Админ-Панель» (видна ролям с правами).	Служебная навигация для администраторов и разработчиков промптов.

Дополнительные элементы верхней панели:
    • Тема оформления — переключение тёмной/светлой темы (запоминается в браузере).
    • «Последнее обновление: DD.MM.YYYY» — дата последнего задеплоенного обновления приложения (раздел «Обновления» админки).
    • Виджет лимитов моделей — для отдельных моделей показывает остаток суточных лимитов (токены/запросы).

5. Режим «Чат с DLAI»
Режим используется для свободного диалога: вопросы, объяснения, идеи, уточнения.
    • Поле ввода принимает обычный текст.
    • Кнопка Send отправляет сообщение; Enter отправляет, Shift+Enter переносит строку.
    • Пока модель отвечает, новый запрос не принимается — дождитесь ответа.
    • Ответы отображаются в виде аккордеона; последняя реплика раскрыта автоматически.
    • Блоки рассуждений модели (think-блоки) сворачиваются в отдельный аккордеон «Показать/Скрыть» — их можно раскрыть отдельно от основного ответа.
    • Clear Context очищает историю диалога и серверный контекст модели для текущей вкладки.
Когда нажимать Clear Context. Если модель начала учитывать старые сообщения, которые больше не относятся к новой задаче, очистка контекста помогает начать новый разговор без «хвоста» предыдущей темы.
История сообщений сохраняется в браузере (localStorage) и не пропадает после перезагрузки страницы; «Очистить контекст» не удаляет видимый чат, а сбрасывает память модели на сервере.

6. Режим «Реши задачу»
Режим предназначен для решения задач по программированию. Пользователь выбирает язык программирования, тему и, при необходимости, препромпт. Без выбранного языка программирования отправка блокируется.
Поле	Обязательность	Как влияет на запрос
Язык программирования	Обязательное	Добавляет контекст «реши задачу на языке …».
Тема	Зависит от языка	Уточняет учебный или технический раздел.
Препромпт	Необязательный	Задаёт стиль и глубину решения.
Текст задачи	Обязательный по смыслу	Условие, которое нужно решить (при входе через ссылку задачи подгружается автоматически).

Если выбрана тема, но препромпт не выбран, интерфейс спросит подтверждение — отправить ли запрос без препромпта.
Фактически система превращает сообщение в структурированный запрос «реши задачу на языке …» плюс выбранный препромпт, поэтому качество заполненных полей напрямую влияет на качество ответа.
Рекомендация. Формулируйте задачу полностью: входные данные, выходные данные, ограничения, примеры и требуемый формат ответа.

7. Режим «В чём ошибка?»
Режим предназначен для поиска ошибки в коде. Заполняются два поля — условие задачи и код программы, плюс язык, тема и препромпт. Должно быть заполнено хотя бы одно из полей: задача или код.
Поле	Что писать	Почему важно
Задача	Условие, ожидаемое поведение, примеры.	Модель понимает, что программа должна делать.
Код программы	Фрагмент или полный код с ошибкой.	Модель анализирует фактическую реализацию.
Язык программирования	Язык кода.	Без языка отправка блокируется.
Тема и препромпт	Контекст и формат разбора.	Помогают получить учебное объяснение, а не просто исправление.

Лучший запрос. Добавьте не только код, но и что именно пошло не так: ошибка компиляции, неверный ответ на тесте, зависание, превышение времени или неожиданное поведение.

8. Выбор модели
Модель выбирается в верхней панели перед отправкой сообщения. В списке отображаются только модели, доступные на текущую дату (доступность проверяется ежедневно в 04:00 МСК администрированием системы).
    • Группа «Часто используемые» — вверху списка стоит самая используемая модель именно вашего аккаунта (по истории успешных запросов).
    • Группа «Все модели» — остальные модели по алфавиту.
    • У каждой модели показываются средняя скорость ответа и процент успешных решений (по накопленной статистике).
    • Сортировку «Все модели» можно переключать: по алфавиту / по скорости / по точности / скорость+точность (запоминается в браузере).
    • Если ни одна модель сейчас недоступна, в списке отображается сообщение «Сегодня нет доступных моделей».
Совет. Модели отличаются по скорости и качеству: быстрые хороши для коротких вопросов, «мыслящие» (Thinking/Reasoning) — для сложных задач, но отвечают дольше.

9. Выбор языка интерфейса и ответа
Переключатель языка (Русский / English / Français) меняет подписи, плейсхолдеры и подсказки интерфейса. Кроме того, выбранный язык передаётся модели как инструкция отвечать на этом языке — на не-русских языках модель обязана отвечать только на выбранном языке, независимо от языка вопроса.

10. Голосовой режим
Кнопка «Голосовой режим» открывает панель голосового ввода и озвучивания ответов. Работает в браузерах с поддержкой Web Speech API (обычно Chrome или Edge).
    • Голосовой ввод: надиктовать сообщение (запись до 30 секунд; распознанный текст отправляется автоматически).
    • Озвучить ответ: включить воспроизведение ответа модели голосом.
    • Стоп: прекратить озвучивание.
    • Опция «Озвучивать think-блоки»: проговаривать также служебные рассуждения.
Ограничение браузера. Если голосовые функции не работают, проверьте браузер, разрешение на микрофон и поддержку Web Speech API.

11. Работа с контекстом и форматирование кода
Контекст диалога помогает модели помнить предыдущие сообщения; это удобно в рамках одной темы и мешает при переходе к новой. Для нового обсуждения используйте Clear Context.
Код рекомендуется оборачивать в тройные обратные кавычки — ответ отображается читабельно и модель не путает код с обычным текстом:
```python
for i in range(5):
    print(i)
```

12. Практические примеры запросов
Ситуация	Пример хорошего запроса	Почему это хорошо
Свободный чат	Объясни простыми словами, чем отличается список от кортежа в Python.	Есть тема и ожидаемый стиль объяснения.
Реши задачу	Дана строка. Нужно посчитать количество гласных. Язык Python. Покажи алгоритм и код.	Указаны входные данные, цель и язык.

Формат ответа	Сначала кратко укажи ошибку, затем объясни причину и дай минимальное исправление.	Модель получает структуру ответа.

## Инструкция для разработчика промптов

1. Назначение и роль
Разработчик промптов — это роль для тех, кто создаёт и улучшает препромпты: управляющие инструкции, которые уточняют поведение модели (стиль, структуру, глубину разбора ответа). Роль доступна всем желающим: группа `prompt_developer` назначается автоматически каждому пользователю при первом входе через `DLSID` (см. `ai/external_account.py`).
Разработчик промптов работает в административном интерфейсе `/ai/admin/`, но имеет ограниченный набор прав: он управляет только своими промптами и видит только свои журналы запросов. Управление моделями, справочниками и глобальными настройками в его зону не входит.

2. Первый вход в админку
    1. Войти на основном сайте `dl.gsu.by`.
    2. Перейти на `/ai/admin/`.
    3. При первом входе система предложит установить локальный пароль на странице `/ai/admin/set-password/` (минимум 8 символов). Пароль нужен для внутренней идентификации в админке; авторизация по-прежнему выполняется через основную сессию.
    4. После входа в шапке отображается ваша роль — «Разработчик промптов».
Адреса, важные для разработчика промптов:
Раздел	Адрес	Что там
Мои промпты	`/ai/admin/prompts/my/`	Список только ваших промптов.
Все промпты	`/ai/admin/ai/prompt/`	Общий список промптов (правка — только своих).
Общие препромпты	`/ai/admin/ai/sharedprompt/`	Просмотр системных шаблонов (правка — только у персонала).
Журнал запросов	`/ai/admin/ai/airequestlog/`	Ваши запросы к моделям.
ARM: Пакетное решение	`/ai/admin/arm/solve/`	Пакетное решение задач DL выбранными моделями.
ARM: Поиск ошибки	`/ai/admin/arm/find-error/`	Прогон одной задачи через несколько моделей.

3. Мои промпты: создание и права
Раздел «Мои промпты» показывает только ваши промпты (владельцем или редактором которых вы являетесь; логика ACL — `ai/querysets.py::prompt_queryset_for_user`). Общий список промптов доступен через раздел «Промпты».
Права на промпт:
    • При создании промпта вы автоматически становитесь его владельцем (`owner`) и редактором (`editors`) — см. `ai/admin/models.py::PromptAdmin`.
    • Вы можете редактировать только свои промпты. Чужие промпты открываются в режиме «только чтение» (все поля readonly).
    • Удалить можно только свой промпт; суперпользователь может удалить любой.
    • Блок «Доступ» (владелец и список редакторов) настраивается только суперпользователем — он решает, кому дать право редактировать ваш промпт совместно.
Создание промпта:
    1. Открыть «Мои промпты» → «Добавить промпт».
    2. Заполнить поля (см. ниже) и сохранить.
    3. Промпт сразу появляется в выпадающем списке препромптов на страницах «Реши задачу» и «В чём ошибка?» — чат-интерфейс показывает все промпты всем авторизованным пользователям (препромпты — учебный контент, а не приватные данные).

4. Поля промпта
Поле	Назначение	Комментарий
Название (RU)	Как промпт отображается в списке.	Короткое и понятное, например «Разбор ошибки пошагово».
Язык программирования	Привязка к языку.	Определяет, в каких задачах промпт логичен.
Тема	Привязка к теме выбранного языка.	Используется для привязки «по теме».
Текст (RU)	Основной текст инструкции.	Главное поле; пишите конкретные инструкции модели.
Name/Text (EN, FR)	Переводы для не-русских языков интерфейса.	Заполняются автоматически (см. ниже).
Общий препромпт / Переопределение текста	Привязка к системному шаблону.	Настраивается персоналом; обычному разработчику промптов трогать не нужно.

Действия со списком промптов:
    • «Автоперевод → EN / FR» — заполняет пустые английские/французские поля через Google Translate (плейсхолдеры `{language}/{topic}/…` защищаются; сервис — `ai/services/auto_translate.py`).
    • «Экспорт выбранных промптов в CSV».
Качество текста. Хороший препромпт не подменяет задание пользователя, а уточняет способ ответа: формат, глубину объяснения, ограничения. Примеры — в разделе «Управление препромптами» инструкции суперадмина.

5. Общие препромпты: что это и почему их нельзя редактировать
«Общие препромпты» (`SharedPrompt`) — это не обычные препромпты, а системные шаблоны трёх режимов: чат, «Реши задачу», «В чём ошибка?». Именно из них собирается каркас запроса к модели, а выбранный пользователем промпт добавляется поверх. В шаблонах используются плейсхолдеры `{language}`, `{topic}`, `{message}`, `{code}`, которые приложение заполняет автоматически.
Разработчик промптов может просматривать общие препромпты, чтобы понимать, во что превращается его промпт, но редактировать их может только персонал (staff/superuser). Порядок настройки шаблонов и привязок — см. инструкцию суперадмина.

6. Как проверить свой промпт
Проверка через пользовательский интерфейс:
    1. Открыть «Реши задачу» или «В чём ошибка?» в чате.
    2. Выбрать язык, тему и свой препромпт.
    3. Отправить тестовый запрос и оценить ответ.
Проверка через ARM (сравнительное тестирование моделей):
    • «Поиск ошибки (ARM)» `/ai/admin/arm/find-error/` — прогон одной задачи (условие + код) сразу через несколько моделей: удобно сравнить, как разные модели соблюдают ваш промпт.

    • Препромпт для ARM берётся из «препромптов по умолчанию» (привязок ARM) — их настраивает суперпользователь (см. `/ai/admin/prompt-defaults/`). Проверяя промпт через ARM, убедитесь, что нужная привязка создана.
Контроль результатов:

## Инструкция для тестера

1. Назначение и область применения
Документ описывает работу тестера в тест-панели и ARM-режиме 'В чем ошибка'. Основной сценарий — проверить одну задачу сразу в нескольких моделях и сравнить ответы по успешности, качеству, скорости, расходу токенов и корректности объяснения.
Инструкция предназначена для QA-специалистов и пользователей, включенных в группу `prompt_developer`. Она помогает проводить сравнение моделей одинаковым способом, чтобы результаты были воспроизводимыми.
Смысл ARM. ARM-тестирование снижает субъективность: одна и та же задача отправляется выбранным моделям, после чего ответы сравниваются по единым признакам.
У ARM есть два режима: «Поиск ошибки» (одна задача через несколько моделей — описан в этой инструкции) и «Пакетное решение» `/ai/admin/arm/solve/` (пакетное решение задач курса dl.gsu.by выбранными моделями с отчётом по проценту решённых). Оба режима доступны членам группы `prompt_developer`.

2. Доступ тестера
Для доступа пользователь должен входить в группу `prompt_developer` (группа назначается автоматически при первом входе через DLSID). После успешного входа пользователь автоматически направляется в ARM-раздел 'В чем ошибка'.
    1. Войти на основной сайт `dl.gsu.by` под своей учётной записью.
    2. Перейти на `/ai/admin/arm/find-error/`.
    3. Убедиться, что после входа открыт ARM-раздел 'В чем ошибка'.
    4. Если доступ запрещен, проверить членство в группе `prompt_developer`.

Пользователь в группе `prompt_developer`	Доступ к тест-панели открыт.	Обратиться к администратору прав.

## Инструкция для системного администратора

1. Назначение и контекст инфраструктуры
Документ описывает инфраструктурные требования и порядок запуска AI-приложения на виртуальной машине. Особое внимание уделено работе за корпоративным прокси, Docker/Docker Compose v2, PostgreSQL, портам, WebSocket и эксплуатационной диагностике.
Цель системного администратора — обеспечить воспроизводимый запуск, сетевую доступность сервиса, корректный доступ к внешним API моделей и предсказуемую диагностику при сбоях.
Главная особенность контура. VM не имеет прямого доступа в интернет: внешний трафик, включая docker pull и обращения к API моделей, должен идти через корпоративный прокси.

2. Требования к виртуальной машине
Компонент	Минимальное требование	Комментарий
ОС	Linux, рекомендуется Ubuntu/Debian.	Желательна LTS-версия и актуальные пакеты безопасности.
Сеть	Доступ к интернету через HTTP/HTTPS-прокси.	Проверяется отдельно для shell, Docker daemon и контейнеров.
Docker	Docker Engine и доступ пользователя к Docker daemon.	Обычно требуется членство в группе docker.
Compose	Docker Compose v2.	Проверяется командой docker compose version.
База данных	PostgreSQL локально или внешне.	Внешний PostgreSQL предпочтительнее для отказоустойчивости.
Порты	8080 или 8081 для nginx, 5432 для PostgreSQL при локальной БД.	Порт 8081 указан как production по умолчанию.
Ресурсы	Минимум 2-4 GB RAM и достаточный диск.	Для стабильной работы желателен запас по RAM и месту под логи.

3. Сетевой доступ и корпоративный прокси
Прокси должен быть настроен на тех уровнях, где выполняются сетевые обращения: shell/systemd, Docker Engine, сборка образов и, при необходимости, runtime контейнеров. Наличие прокси только в пользовательской shell-сессии не означает, что Docker daemon сможет скачивать образы.
3.1. Системный прокси
Системные переменные HTTP_PROXY, HTTPS_PROXY и NO_PROXY задают базовые правила выхода в сеть для командной оболочки и сервисов, которые наследуют окружение.
export HTTP_PROXY="http://user:pass@proxy.host:3128/"
export HTTPS_PROXY="http://user:pass@proxy.host:3128/"
export NO_PROXY="localhost,127.0.0.1,db,nginx,.local"

Пароли и спецсимволы. Если в логине или пароле есть специальные символы, их следует указывать в URL-encoded виде, иначе прокси может отклонять запросы.

4. Прокси для Docker Engine и сборки образов
Docker daemon является отдельным системным сервисом. Поэтому для скачивания образов прокси настраивается через systemd drop-in файл.
    1. Создать каталог /etc/systemd/system/docker.service.d.
    2. Создать файл http-proxy.conf с переменными окружения.
    3. Выполнить daemon-reload и перезапустить Docker.
    4. Проверить docker info | grep -i proxy.

# Сисадмин: инфраструктура и запуск

Этот документ дополняет базовые инструкции по развертыванию и описывает системные требования, прокси и нюансы виртуальной машины.

## 1. Контекст инфраструктуры

- Проект разворачивается на виртуальной машине (VM).
- VM находится за корпоративным прокси, поэтому для доступа к внешним API и скачивания образов нужен прокси.
- Основные зависимости на стороне сервера: Docker, Docker Compose v2 и PostgreSQL.

## 2. Требования к VM

- ОС: Linux (рекомендуется Ubuntu/Debian).
- Доступ к интернету только через прокси (HTTP/HTTPS).
- Открыт доступ к Docker daemon для пользователя (обычно группа docker).
- Свободные порты:
  - 8080 (dev-like) или 8081 (prod по умолчанию) для nginx контейнера.
  - 5432 для PostgreSQL (если БД на той же VM).

## 3. Настройка прокси

### 3.1. Системный прокси (если требуется)

Настройте переменные окружения на уровне shell или systemd:

- HTTP_PROXY
- HTTPS_PROXY
- NO_PROXY

Пример (в bash):

export HTTP_PROXY="http://user:pass@proxy.host:3128/"
export HTTPS_PROXY="http://user:pass@proxy.host:3128/"
export NO_PROXY="localhost,127.0.0.1,db,nginx,.local"

Если в логине/пароле есть спецсимволы, указывайте их в URL-encoded виде.

### 3.2. Прокси для Docker Engine

Если Docker должен выходить в интернет (pull образов), настройте прокси для демона.

1) Создайте каталог:

sudo mkdir -p /etc/systemd/system/docker.service.d

2) Создайте файл /etc/systemd/system/docker.service.d/http-proxy.conf:

[Service]
Environment="HTTP_PROXY=http://user:pass@proxy.host:3128/"
Environment="HTTPS_PROXY=http://user:pass@proxy.host:3128/"
Environment="NO_PROXY=localhost,127.0.0.1,db,nginx,.local"

3) Примените изменения:

sudo systemctl daemon-reload
sudo systemctl restart docker

4) Проверка:

docker info | grep -i proxy

### 3.3. Прокси для сборки образов

Если используется docker-compose.linux.yml, обратите внимание:
- В секции build args можно передавать HTTP_PROXY/HTTPS_PROXY только для сборки.
- В runtime переменные прокси могут быть отключены, если это нужно по политике безопасности.

## 4. Установка Docker и Compose

### 4.1. Docker Engine

Рекомендуемый способ (Ubuntu):

- Установить официальный репозиторий Docker.
- Установить docker-ce и docker-ce-cli.
- Добавить пользователя в группу docker:

sudo usermod -aG docker $USER

После этого перезайдите в сессию или выполните:

newgrp docker

Проверка:

docker version

### 4.2. Docker Compose v2

Проверка:

docker compose version

Если команда отсутствует, установите пакет docker-compose-plugin.

## 5. PostgreSQL

Варианты:
- Локальный PostgreSQL на той же VM.
- Внешний PostgreSQL (рекомендуется для отказоустойчивости).

Минимальные параметры подключения указываются в .env:

- DB_HOST
- DB_PORT (обычно 5432)
- DB_USER
- DB_PASSWORD
- DB_NAME

Убедитесь, что пользователь имеет права на создание таблиц и миграции.

## 6. Запуск контейнеров (рекомендованный порядок)

1) Создать .env и заполнить ключевые переменные.
2) Поднять стек:

docker compose --env-file .env up -d --build
docker compose --env-file .env exec -T web python manage.py migrate

docker compose --env-file .env exec -T web python manage.py migrate

3) Проверить статус:

docker compose ps

4) Проверить доступность:

curl -I http://127.0.0.1:8081/ai/chat/

## 7. Нюансы эксплуатации на VM

- Если VM не имеет прямого доступа к интернету, весь внешний трафик (API моделей, docker pull) должен идти через прокси.
- В случае 401/403/429 от моделей проверяйте:
  - валидность токенов в .env,
  - доступ к конкретной модели у провайдера,
  - корректность прокси (не подменяет ли ответы).
- Для WebSocket /ai/chat/ws/ убедитесь, что внешний nginx пропускает Upgrade и Connection: upgrade.

## 8. Диагностика

## Инструкция для суперадмина

1. Назначение и область применения
Настоящая инструкция описывает работу суперадминистратора в административном интерфейсе AI-приложения `/ai/admin/`. Документ раскрывает порядок входа, полный пул разделов и настроек, управление справочниками, препромптами и привязками ARM, глобальное включение AI, контроль состояния моделей, логи, регрессионное тестирование промптов, тестовую консоль и журнал обновлений.
Ключевая идея. Суперадмин управляет не отдельным диалогом пользователя, а конфигурацией всей AI-системы: доступностью интерфейса, набором справочников, препромптами, привязками ARM и состоянием моделей.

Topic	`/ai/admin/ai/topic/`	Темы, привязанные к языкам; для тем доступны действия «Автоперевод → EN / FR».
Prompt	`/ai/admin/ai/prompt/`	Препромпты, привязанные к темам (в UI — выпадающий список препромптов).
SharedPrompt	`/ai/admin/ai/sharedprompt/`	Системные шаблоны режимов chat/solve/find_error с плейсхолдерами `{language}/{topic}/{message}/{code}`.

Порядок настройки:
    1. Создать или проверить язык программирования.
    2. Создать тему и привязать её к языку.
    3. Создать промпт и привязать к теме (или к общему препромпту).
    4. Проверить отображение в пользовательском интерфейсе и выполнить пробовый запрос.
Автоперевод: действие «Автоперевод → EN / FR» на страницах Темы/Промпты/Общие препромпты заполняет пустые переводы (Google Translate); пакетно — команда `python manage.py auto_translate` (флаги `--model`, `--overwrite`, `--dry-run`).

5. Препромпты по умолчанию (привязки ARM)
Раздел `/ai/admin/prompt-defaults/` (только суперпользователь) управляет привязками `ArmPromptBinding` (`ai/models.py`): комбинация «язык программирования + тема + вид ARM» → промпт.
Зачем нужно. На страницах ARM промпт не выбирается вручную — он подставляется автоматически из привязок: сначала ищется точное совпадение по теме, при отсутствии — привязка ко всему языку. Без привязки ARM-прогон для этого языка/темы идёт без препромпта.
    1. Открыть «Препромпты по умолчанию».
    2. Создать привязку: язык, тема (или пустая = весь язык), вид ARM (пакетное решение / поиск ошибки).
    3. Выбрать промпт и сохранить.
    4. Проверить подстановку на соответствующей ARM-странице.

6. Контроль состояния моделей
Раздел «Состояние моделей» (`/ai/admin/arm/models/`) отображает таблицу доступности моделей текущего окна проверки (`AIModelAvailability`/`AIModelHealthRun`).
Элемент	Что показывает	Как интерпретировать
Статус модели	Активна или неактивна.	Неактивная модель не показывается пользователям.
Дата окна проверки / время последней проверки	Актуальность результата.	Если устарело — ручное обновление.
Кнопка обновления	Запускает фоновую перепроверку всех моделей.	После смены токенов, прокси или провайдеров; прогресс показывается на странице.
Плановая проверка выполняется ежедневно в 04:00 МСК (`ai/model_health.py`); при недоступности бот-пулов Web DeepSeek/Web Kimi приложение автоматически перезапускает пул и перепроверяет модель (управляется переменными `AI_WEB_DEEPSEEK_AUTORECOVERY` / `AI_WEB_KIMI_AUTORECOVERY`, по умолчанию включено).
Ручной запуск:
    python manage.py check_models_health
    python manage.py check_models_health --force
Самовосстановление. Если у пользователей ни одна модель недоступна, открытие любой страницы `/ai/` само запускает фоновую перепроверку — не нужно ждать 04:00 или запускать команду вручную.

7. ARM-тестирование
ARM используется для сравнительной проверки моделей.
    • «Поиск ошибки» `/ai/admin/arm/find-error/`: одна задача (условие + код) прогоняется через несколько моделей последовательно; краткий отчёт (всего/успешно/ошибки/токены/самая быстрая), карточки полных ответов, человекочитаемые ошибки (таймаут, 401, 429…).
    • «Пакетное решение» `/ai/admin/arm/solve/`: выбор моделей, языка (расширение файла), темы, загрузка дерева задач курса DL, отметка задач, опционально `dl_test` и (для суперпользователя) «заносить результаты в БД»; каждая задача×модель даёт вердикт (решена/не решена/пропущена) по детерминированному сравнению с образцом DL (`ai/grading.py`, порог 0.85, без LLM-судьи), либо отправляет решение в DL при `dl_test`.
Результаты пакетного прогона: таблица по каждой паре задача×модель (статус, вердикт, время, токены, код — скачивается файлом), сводка по моделям (% решённых), XLSX-отчёт; кнопка отмены; возвращение на страницу без параметров показывает последний ваш прогон.
Для суперадмина ARM полезен как инструмент контроля качества конфигурации: стабильные ошибки части моделей — это, как правило, доступность модели, токен, прокси или провайдер, а не пользовательский запрос.

8. Журнал запросов
Раздел `/ai/admin/ai/airequestlog/`. Таблица содержит: время отправки и получения, пользователя, язык программирования, тему, препромпт, модель, статус, режим, длительность, токены.
    • Фильтры: статус, источник, режим, модель, пользователь, диапазон дат, полнотекстовый поиск `q` (по сообщению, ответу, контексту), поиск по номеру задачи.
    • По клику на строку открывается детальная страница `/ai/admin/ai/airequestlog/<id>/`: полный запрос, полный ответ, техническая ошибка.
    • Действия: экспорт записи в XLSX, повторная отправка (resend), повторный ARM-прогон из лога (rerun-arm).
    • Разработчики промптов видят в журнале только свои записи — ограничение встроено в раздел.

9. Регрессионные тесты промптов
Раздел `/ai/admin/prompt-regression/` (только суперпользователь) — автоматическая проверка промптов на тест-кейсах.
    • Тест-кейсы (`PromptTestCase`, `/ai/admin/ai/prompttestcase/`): название, режим (solve/find_error/chat), язык, тема, входной текст, ожидаемый ответ, компаратор.
    • Компараторы (`ai/grading.py`): `ratio` (доля совпадения с порогом), `contains_all` (все подстроки), `exact`, `set` — детерминированные, без LLM-судьи.
    • Прогон: выбирается один промпт и одна модель, сообщения собираются тем же компоузером, что и в чате (`ai/services/message_composer.py`), поэтому правки промпта сразу попадают в тесты.
    • Отчёт: всего/совпало/не совпало/пропущено/токены, разбивка по режимам, полный список расхождений с подсказками.
    • CLI-аналог: `python manage.py run_prompt_tests --model <ключ> [--prompt id] [--cases 1,2,3]`.

10. Тестовая консоль
Раздел `/ai/admin/test-console/` (только суперпользователь) запускает полный набор Django-тестов приложения (`manage.py test ai`) в изолированном сабпроцессе — безопасно для работающего прод-сервера.
    • Одновременный второй прогон не допускается (single-flight).
    • Прогресс отображается полосой (общее число тестов считается до запуска); после завершения — сводка (прошло/падений/ошибок/пропущено, секунды) и разбор по классам.
    • Полный вывод каждого прогона сохраняется в `logs/test_console/` (последние 10) и доступен через «История логов»; страница показывает последний ваш прогон без `?run_id=` в течение 10 минут.
    • Прогон виден в меню «Мои процессы» в шапке.

11. «Мои процессы» (меню в шапке)
Выпадающее меню «Мои процессы» в шапке админки (`ai/admin/active_runs.py`, скрипт `static/admin/js/ai_processes.js`) показывает личные активные и завершённые за последние 10 минут процессы пользователя: ARM-прогоны, регрессионные тесты, тестовую консоль. Отдельно показывается безличная запись «обновление моделей» — она глобальная и видна всем администраторам.
Механика для новых точек старта: после успешного запуска процесса фронт должен диспатчить `ai-processes:refresh`, чтобы меню обновилось немедленно.

12. Обновления
Раздел `/ai/admin/updates/` (только суперпользователь) — таблица коммитов ветки `main` (`UpdateLog`): дата, описание на русском, автор; фильтры по автору и датам, поиск, пагинация 50.
Наполнение:
    • Команда `python manage.py sync_update_log` (`--rebuild` для полной пересборки).
    • Автоматически: при старте контейнера (Dockerfile CMD) и через git-хуки post-merge/pre-push (`bash scripts/setup_hooks.sh` после clone).
Дата последнего обновления отображается в чате («Последнее обновление»).

## Инструкция для разработчика

1. Назначение и область применения
Эта инструкция предназначена для разработчиков, которые вносят изменения в код DL.AI. Она описывает архитектуру, порядок локальной разработки, ключевые подсистемы, тестирование и соглашения по работе с репозиторием. Полная техническая документация находится в файле [doc/Документация для разработчика.md](doc/Документация%20для%20разработчика.md).

2. Требования к окружению
Для локальной разработки без Docker нужны Python 3.11+, PostgreSQL 14+ и psql. Для Docker-разработки достаточно Docker Engine, Docker Compose v2 и свободных портов 8080 (dev) или 8081 (prod).

3. Локальный запуск без Docker
    1. Создать базу и пользователя PostgreSQL.
    2. Скопировать .env.example в .env и выставить DB_HOST=127.0.0.1.
    3. Создать виртуальное окружение, установить зависимости, выполнить миграции.
    4. Запустить python manage.py runserver 0.0.0.0:8000.
    5. Открыть http://127.0.0.1:8000/ai/...

4. Локальный запуск в Docker
    1. Скопировать .env.example в .env и выставить DB_HOST=db.
    2. Запустить docker compose --env-file .env up -d --build.
    3. Выполнить миграции и collectstatic внутри контейнера web.
    4. Открыть http://localhost:8080/ai/...

5. Git workflow
    1. Каждый разработчик работает в отдельной ветке, названной по фамилии.
    2. По готовности открывается Pull Request в main.
    3. PR проверяется и мерджится в main.
    4. Изменения выкатываются на production.
Перед началом работы новый участник отправляет письмо на vadik2005guryanov@gmail.com с GitHub nickname и почтой для связи.
